## 맥락 (Context)

기존 Wireweave 는 한 번에 한 화면을 텍스트 DSL 로 적고 그 한 화면을 미리보기하는 구조였다. 또 한때 AI 에이전트·스킬·마켓플레이스를 "출시 예정"으로만 노출하고 에디터의 에이전트 기능을 운영자에게만 여는 보류 노선(랜딩 v2.0 출시예정 톤 + 에디터 admin 게이팅)을 잡았었는데, 그 보류의 실제 이유는 "유료화를 못 한다"는 오해였다.

두 전제가 풀렸다. 첫째, 결제·구독은 사업자 등록이 없어도 MOR(Merchant of Record, 예: Paddle) 서비스로 웹·데스크탑에서 정상 운영할 수 있다(사업자 등록이 필요한 것은 모바일 인앱결제 한정). 둘째, 사용자의 Claude 구독을 데스크탑에서 쓰는 것은 우회가 아니라 Anthropic 이 공식 지원하는 Agent SDK 경로다(별도 전용 크레딧은 시행 보류 상태이나, 그동안에도 구독의 표준 사용 한도에서 정상 차감된다).

그래서 2.0 은 "보류·출시예정"이 아니라, 제품의 작업 패러다임 자체를 바꾸는 정식 릴리즈로 확정한다. 핵심 질문은 "한 화면 도구를 넘어, 사람이 임의 프롬프트로 와이어프레임을 뽑는 것보다 훨씬 높은 품질을, 실제 개발까지 이어지는 산출물로 만들려면 무엇을 묶어야 하는가"였다.

## 결정 (Decision)

2.0 의 범위·과금·뷰·재사용 전략을 다음과 같이 확정한다. 아래 항목은 모두 **동시 출시**이며, "출시 예정"으로 남기는 항목은 없다 — 기존 보류 노선(랜딩 출시예정 톤 + 에이전트 admin 게이팅)은 이 결정으로 폐기된다.

**1. 웹 대시보드 — 무한 캔버스 다중 화면**
- 한 캔버스에 한 화면이 아니라, Figma·Google Stitch 처럼 **무한 캔버스 위에 여러 화면을 함께 배치·렌더**한다. 다중 화면 구성이 주(主), 단일 화면 코드 패널은 부차로 격하한다.
- 화면을 클릭하면 — Figma 가 CSS·좌표를 보여주듯 — 그 화면의 **Wireweave 코드와 DOM 구조**를 보여준다. 단, 우리는 디자인(색·그림자·브랜딩)이 없는 **순수 와이어프레임** 기반이라는 점이 결정적 차이다.
- **AI 에이전트가 와이어프레임을 실제로 생성**한다.

**2. 데스크탑 앱 — 현 Wireweave Studio 의 개조**
- 현재 시나리오 기반 문서 작성 + 화면 구성 데스크탑 앱을, **SSOT 문서 구축(인터뷰 기반) + 와이어프레임 생성**으로 재편한다.
- LLM 접근은 두 갈래를 모두 지원한다: (a) **사용자의 Claude 구독을 쓰는 공식 Agent SDK 경로**(현재는 구독 표준 사용 한도에서 차감, 전용 크레딧은 Anthropic 측 보류), (b) **사용자가 직접 넣는 API 키(BYOK, 로컬 저장)**. 데스크탑은 토큰 원가를 우리가 지지 않으므로 플랫폼 기능료(flat) 모델이다.

**3. SSOT 셋트 — 인터뷰로 짓는 제품 스펙 + 와이어프레임 (핵심 신규)**
- 별도 SSOT 도구(ssot-studio)의 방법론을 채택한다: 12종 노드(Platform·Persona·Domain·Concept·Capability·SystemComponent·Integration·Invariant·Decision·Screen·Endpoint·Flow), 4축 측면, 빈칸 일급, 자기완결·역도출 가능성.
- 단 ssot-studio 가 **코드에서 문서를 추출**하던 방식(코드 추출 레시피 + 코드→문서 커버리지)을, **사용자에게 질문·인터뷰해 정보를 수집하는 인터뷰 엔진**으로 대체한다. 더 추상적이고 추론이 많은 작업이며, 빈 문서 골격(skeleton)의 각 빈 항목이 곧 인터뷰 질문이 된다.
- **12종 전체**를 채워 "실제 제품 스펙" 수준의 문서를 만들고, 이를 컨텍스트로 와이어프레임을 생성한다. 목표는 **산출물(SSOT 문서 + 와이어프레임)로 실제 개발까지 가능**하게 하는 것이다. 임의 프롬프트로도 생성은 가능하되, 인터뷰로 구축한 SSOT 컨텍스트가 더 높은 품질을 보장한다.
- 화면을 다루는 **Screen 노드와 캔버스의 와이어프레임은 같은 정체성으로 묶여 양방향 동기**된다(와이어프레임을 편집하면 그 변화가 Screen 노드 본문/Flow 엣지로 역반영). Wireweave 코드·DOM 이 결정론적이라 역파싱 앵커가 명확한 점을 활용한다.
- SSOT 문서는 **웹 대시보드와 데스크탑 앱 양쪽에서** 구축·열람한다.
- 구현은 ssot-studio 를 그대로 임베드하지 않고, 그곳의 schema·skeleton·scripts·methodology 를 **복사 + 개선 + 수정해 내장 기능으로 별도 구성**한다.

**4. SSOT 그래프 뷰 = 3D**
- SSOT 노드-관계 그래프를 **3D** 로 보여준다(참고 구현 ssot-web 은 2D). 채택 스택: `react-force-graph-3d`(Three.js/WebGL) + `d3-force-3d` + `troika-three-text`, 기존 2D(@xyflow) 뷰 옆에 지연 로드 토글. kind 별 soft 레이어링 또는 클러스터링으로 가독성을 준다. Tauri(WKWebView, WebGL2)에서 동작한다.

**5. 과금·정책 골격**
- 웹/데스크탑 결제는 **MOR(Paddle)** 로 사업자 등록 없이 운영한다(모바일 인앱결제만 사업자 등록 제약).
- 웹은 **구독 + 월 토큰 쿼터(매니지드 게이트웨이, 하드캡 + 초과분 원가 패스스루)**, 데스크탑은 **BYOK 또는 구독 Agent SDK + flat 기능료**.

## 근거와 결과 (Consequences)

**왜 이 묶음인가.** SSOT 의 Screen 노드는 "이 화면에서 누가 무엇을 하고, 무슨 데이터를 보고/입력하며, 어떤 규칙이 적용되고, 어떤 기능을 호출하는가"를 담는다 — 이는 임의 프롬프트 한 줄과 비교할 수 없는, 화면별 와이어프레임 생성에 필요한 구조화된 컨텍스트 그 자체다. Flow 와 화면 간 전이 엣지는 무한 캔버스의 다중 화면 배치도가 된다. 즉 "SSOT 문서를 짓는 것"과 "다중 화면 와이어프레임을 만드는 것"은 같은 그래프의 양면이며, 둘을 셋트로 묶으면 생성 품질이 grounding 으로 올라가고 산출물이 실제 개발 입력이 된다.

**따라오는 것(영향 후보).**
- `domain.ai-editor` 는 단일 화면 편집에서 무한 캔버스 다중 화면 작업 공간으로 재편된다.
- `domain.agent-chat`/`domain.ai-generation` 은 SSOT 컨텍스트 주입 경로가 추가된다.
- `domain.account-billing` 에 웹 토큰 쿼터·하드캡, 데스크탑 BYOK/구독·flat 요금이 추가된다.
- `domain.distribution` 에 데스크탑(Tauri) 배포 채널이 추가된다.
- 새로 만들어야 할 대상: 무한 캔버스 다중 화면 뷰, SSOT 인터뷰 엔진, SSOT↔와이어프레임 동기 계층, 3D 그래프 뷰, 내장 SSOT 도구(ssot-studio 포팅본). 이들은 아직 노드가 없다(빈칸).

**전제 정정(이 결정이 바로잡은 것).**
- "사업자 등록이 없어 결제·구독 불가" 는 **모바일 한정**이다. 웹/데스크탑은 MOR 로 가능 — 글로벌 빌더 룰을 그렇게 정정했다.
- 사용자의 Claude 구독을 데스크탑 Agent SDK 로 쓰는 것은 **공식 지원**이다. 2026-04 의 제3자 하니스 차단(구독 인증을 리버스한 도구)과는 별개다. 단, 6/15 시행 예정이던 별도 Agent SDK 전용 크레딧은 **현재 보류**되어, 그동안에는 구독의 표준 사용 한도에서 차감된다(Anthropic 이 사전 고지 후 정책을 바꿀 수 있음 — 운영 모니터링 대상).
